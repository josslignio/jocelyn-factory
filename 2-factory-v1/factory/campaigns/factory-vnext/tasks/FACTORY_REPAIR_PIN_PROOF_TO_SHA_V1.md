# FACTORY_REPAIR_PIN_PROOF_TO_SHA_V1 — Cohérence des reçus de build avec le commit exact qu'ils décrivent (qualité logicielle, pas de sécurité)

## Objectif
Travail de fiabilité logicielle sur notre propre outil de build : chaque reçu (résultat de test, règlement de jalon, promotion, relecture) doit référencer le commit git exact sur lequel il a été produit — vérifier HEAD avant et après, comparer le contenu des fichiers commités, et ne jamais se fier à un nom de branche qui bouge ni au contenu non commité de l'index. Il s'agit de corriger des bugs de cohérence (mauvais SHA copié, fichier non commité pris pour commité), rien d'autre.

## Contrat
Pour CHAQUE id ci-dessous : test qui reproduit le défaut (rouge), correctif minimal au fichier:ligne cités, test vert, et une ligne dans
`factory_v2/audit/CODE_REVIEW_2026-09/REPAIRS_PIN_PROOF_TO_SHA.json` : `{"id", "status": "FIXED|WONTFIX", "commit", "test", "note"}` (WONTFIX seulement démontré par un test). ≥ 80 % FIXED.
Livrables de la synthèse (à honorer en plus des constats) :
- Revue des fonctions qui écrivent/lisent un reçu : SHA observé vs SHA copié, contenu commité vs working tree
- Fusion/promotion sur un SHA fixe, jamais un nom de branche ; l'index ne doit contenir que les fichiers attendus (sinon erreur claire)
- Résolution des conflits de fusion limitée aux fichiers d'état listés ; contenu fusionné relu après coup
- Empreinte déterministe des fichiers sources réellement exécutés (y compris les petits fichiers qui délèguent) pour les digests de validation
